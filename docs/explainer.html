01First, what is DataHub?

Imagine a company with thousands of database tables, dashboards, and machine-learning models. Nobody can track what connects to what. DataHub is an open-source "catalog" — a Google Maps for a company's data.

It answers questions like: what tables exist and what are their columns? Who owns this data? And the killer feature — lineage: the family tree showing how data flows from raw tables, into features, into models, into production.

DataHub stores this entire chain. It's the map. But today, a human still has to read that map and figure out what a change means.

02The problem: silent failures

The ML failures that cost the most money are the ones where everything technically passes — no error is ever thrown — but the meaning of the data quietly changes.

Unit change

Dollars → cents

An upstream team switches revenue from dollars to cents to kill rounding errors. Same name. Same type. No nulls. Pipeline green. Your pricing model now thinks everything costs 100× more.

Meaning drift

Redefined column

is_active used to mean "logged in this month." Now it means "account not deleted." Same boolean. Suddenly 90% of users are "active." Your churn model is silently invalidated.

The trap: a schema check sees no change (same name, same type). A null check sees no nulls. A statistical monitor might not flag a clean 100× shift as "anomalous." The model just gets quietly worse, for weeks, with zero alerts. Nobody catches it — until the money's gone.

03The agent: Semantic Guardian

One reasoning engine — "understand what every column actually means" — pointed at every place DataHub currently needs a human's judgment.

The agent runs this loop end-to-end:

  1. Detect — spots a semantic shift that passed every existing check (a scale jump on the same type, a null-rate collapse, a categorical remap, a currency cue).
  2. Reason over lineage — walks the DataHub graph to find exactly which features, models, and live deployments are affected. This is the "blast radius."
  3. Validate with a human — presents a one-click judgment: the evidence, the reasoning, and a proposed fix. The human confirms in seconds instead of investigating for hours.
  4. Write back to the catalog — records the validated finding (tags, descriptions, glossary, and an incident) into DataHub itself, so the next person or agent inherits the knowledge.
  5. Heal — opens a ready-to-merge fix PR against the pipeline repo. A human clicks merge. It never auto-merges into production.
The same engine also: flags un-tagged sensitive data (PII/governance) and auto-writes the missing documentation that leaves most catalogs 60% empty. One brain, three of DataHub's biggest manual bottlenecks.

3bHow the fix & the PR actually work

"Opens a fix PR" is the part people gloss over, so here's the real mechanism — nothing hand-wavy.

What a "PR" is

A Pull Request (PR) is the standard way developers propose a code change on GitHub. You don't edit live code directly — you submit a suggested change, and a human reviews it and clicks "merge" to accept. Think of it like a suggested edit in a Google Doc: proposed, not applied, until someone approves.

How the agent builds the fix

Once the human confirms the finding is real, the agent generates the correction. Crucially, it doesn't guess — it grounds the fix in what DataHub actually knows:

  1. Locate the code — from the lineage, the agent knows which pipeline/transformation file produces the broken column (e.g. the dbt model or Airflow task that builds avg_order_value).
  2. Read the real schema first — it pulls the true, current schema and stats from DataHub via the MCP Server, so the patch matches reality instead of assumptions. (This is the whole "metadata-aware code" idea — read before you write.)
  3. Generate a scoped patch — for the detected class of change. For a dollars→cents shift: divide the column by 100 (or pin the expected unit and assert it). For a null→0 re-encoding: restore the null-handling. The change is small, targeted, and explained.
  4. Open the PR — the agent commits the patch to a new branch and opens a Pull Request on the repo, with a title, a plain-English explanation of what broke and why, and a link back to the DataHub incident it filed.
  5. Human reviews & merges — you read the diff, and click merge (or don't). The agent never merges to production itself.

Why not auto-merge? Because no serious data team lets a bot push code straight to production — and pretending otherwise would scare a judge, not impress one. The value is that the agent does the ~95% of grunt work (find it, diagnose it, write the fix, explain it) and hands a human a clean, reviewed diff. That's "human-in-the-loop," and it's a feature, not a limitation.

04Why this is genuinely novel

This isn't a hunch. We validated it two ways: against DataHub's own product documentation, and against every major data-quality and ML-monitoring tool on the market today.

No existing tool does this

Every data-quality and ML-monitoring tool is statistics-and-schema shaped. None reasons about a column's meaning changing while its name and type stay valid.

DataHub says this out loud

From DataHub's own blog, published the week the hackathon launched:

"Auto-generation captures how data has been used, not how it should be used… Without a human validation layer, agents retrieve the most popular context, not the most correct context." — DataHub blog, "AI Agents & Human-Validated Context" (July 2026)

In other words: DataHub is a metadata store with no reasoning layer. It stores the ingredients — lineage, stats, schema history — but validating what data should mean is manual human work today. Semantic Guardian is that missing validation layer. We're not rebuilding DataHub; we're building the brain it was designed to host.
